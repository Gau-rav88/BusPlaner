**Project:** Delhi Real-Time Bus Traffic Prediction & Journey Planner (Problem 1)  
**Governing Specification:** PRD v3.0  
**Audit Scope:** Timetable Freshness State Consistency & Warning Propagation  
**Overall Operational Status:** **DEGRADE**  
**Audit Date:** 2026-11-21  

---

## 1. Executive Summary

This independent audit investigates the GTFS timetable freshness handling, canonical state consistency, and warning propagation throughout the Milestone 6 FastAPI REST backend.

The audit verified:
1. **Resolution of State Naming Discrepancy:** The canonical internal freshness enum is strictly `UNAVAILABLE` (`TimetableStatus.UNAVAILABLE`), which was previously conflated with the HTTP 503 error code `TIMETABLE_UNAVAILABLE` in documentation. The API now consistently reports `timetable_status="UNAVAILABLE"` in schema definitions and error envelopes.
2. **Four Canonical Freshness States:** All four states (`CURRENT_VERIFIED`, `EXPIRED`, `ASSUMED_RECURRING`, `UNAVAILABLE`) operate deterministically across the REST layer.
3. **Strict Expired Schedule Rejection:** Queries on dates beyond GTFS validity (e.g. October/November 2026 vs. feed expiration `2024-01-01`) without explicit client opt-in fail closed with `HTTP 400 Bad Request` and `EXPIRED_TIMETABLE`.
4. **Explicit Opt-In Required for Demonstration Mode:** Passing `allow_assumed_recurring=true` enables routing under demonstration mode, clearly asserting `timetable_status="ASSUMED_RECURRING"` and `is_verified_current_service=false`.
5. **Freshness Warnings Reach Every Affected Journey and Leg:** A defect in Milestone 6 where `TransitLeg.warning` omitted the stale timetable warning was identified and corrected. Stale timetable warnings now propagate seamlessly to:
   - The top-level response envelope (`stale_timetable_warning`),
   - The journey alternative warning list (`journey.warnings`), and
   - Every individual transit leg (`leg.warning`).
6. **No Assertion of Physical Operations:** Static GTFS timetable validity does not prove physical bus movement. The API unreservedly asserts `actual_operations_verified: false` across all responses.

## 2. Canonical Freshness State Mapping & Reconciled Nomenclature

In Milestone 6 documentation, the string `TIMETABLE_UNAVAILABLE` was listed under "Freshness States" in one table, causing ambiguity with `UNAVAILABLE`. This audit inspected the underlying codebase and established the canonical representation:

### Canonical State Table

| State Enum | Internal Representation (`TimetableStatus`) | Public API JSON `timetable_status` | Trigger Condition / Invariant | HTTP Code |
|:---|:---|:---|:---|:---:|
| **`CURRENT_VERIFIED`** | `TimetableStatus.CURRENT_VERIFIED` | `"CURRENT_VERIFIED"` | Requested service date is within published feed window (`2022-01-01` to `2024-01-01`). Provenance documented. | `200 OK` |
| **`EXPIRED`** | `TimetableStatus.EXPIRED` | `"EXPIRED"` | Service date is outside feed validity and caller passed `allow_assumed_recurring=false`. | `400 Bad Request` (in `/journeys/plan`) / `200 OK` (in `/timetable/status`) |
| **`ASSUMED_RECURRING`** | `TimetableStatus.ASSUMED_RECURRING` | `"ASSUMED_RECURRING"` | Service date is outside feed validity and caller explicitly passed `allow_assumed_recurring=true`. | `200 OK` |
| **`UNAVAILABLE`** | `TimetableStatus.UNAVAILABLE` | `"UNAVAILABLE"` | Timetable file missing, SQLite database unreadable, or memory structure empty. | `503 Service Unavailable` |

### Distinction Between State and Error Code
- **Canonical State Field:** `timetable_status = "UNAVAILABLE"` (used in all status models).
- **HTTP 503 Error Code:** `error = "TIMETABLE_UNAVAILABLE"` (used as the actionable error envelope identifier).
- **Resolution:** In `backend/app/api/v1/journeys.py`, the 503 error envelope now explicitly includes `"timetable_status": "UNAVAILABLE"` alongside `"error": "TIMETABLE_UNAVAILABLE"`, eliminating any potential client ambiguity.

## 3. Freshness Warning Propagation Audit

### 3.1 Defect Identified in Milestone 6
During inspection of `backend/core/journey_planner.py` (lines 348–378), the `warnings` list for each `TransitLeg` was initialized as `warnings: List[str] = []` and only appended `pred.warning` from segment travel-time predictions. The `timetable_warn` generated by `self.timetable.check_freshness()` was stored on `PlannedJourney.timetable_warning`, but was omitted from individual `TransitLeg.warning` fields.

Consequently, while the top-level journey carried the stale timetable warning, transit legs within the journey had `warning: null` unless a segment-level prediction warning occurred.

### 3.2 Corrective Action Implemented
1. In `backend/core/journey_planner.py`:
   ```python
   warnings: List[str] = []
   if timetable_warn:
       warnings.append(timetable_warn)
   ```
2. In `backend/app/services/planner_service.py`:
   Added fallback safety during schema transformation to ensure `TransitLegSchema.warning` reflects `pj.timetable_warning` if present.

### 3.3 Verification
Automated test `test_freshness_warning_propagation_to_every_leg` in `backend/tests/test_milestone6_1_audit.py` validates that querying `2026-10-01` with `allow_assumed_recurring=true` produces:
- `data["stale_timetable_warning"]`: Contains `"STALE TIMETABLE WARNING"`.
- `j["warnings"]`: Contains `"STALE TIMETABLE WARNING"`.
- Every `TransitLegSchema["warning"]`: Contains `"STALE TIMETABLE WARNING"`.
Conversely, `test_current_verified_leg_has_no_stale_warning` verifies that historical dates within feed validity (`2023-05-15`) produce `CURRENT_VERIFIED` with zero stale timetable warnings.

## 4. Operational Readiness & Physical Ground-Truth Disclosures

The audit evaluated whether any response could mislead operators into assuming physical bus tracking:
1. **`actual_operations_verified` Field:**
   - Evaluated on `GET /api/v1/timetable/status` -> strictly `False`.
   - Evaluated on `POST /api/v1/journeys/plan` (per journey) -> strictly `False`.
   - Evaluated on `GET /api/v1/health` -> strictly reflects status `DEGRADE`.
2. **Feed Validity vs Real-World Operations:**
   Even when `timetable_status == "CURRENT_VERIFIED"`, `actual_operations_verified` remains `False`. Published GTFS schedules represent intended timetables, not observed physical vehicle runs.
3. **Heuristic Confidence vs Probability:**
   Every transit leg explicitly sets `confidence_score_type="HEURISTIC"` and `confidence_explanation="Heuristic score representing operational and empirical data support; NOT a calibrated probability."`.
